# ig-autopost

Автопостинг в два Instagram-аккаунта (`personal`, `goszakupki`) через официальный
Instagram Graph API. Публикация идёт по расписанию через GitHub Actions
(каждые 30 минут проверяет `queue.json`), медиафайлы раздаются через GitHub Pages.

Репозиторий публичный: github.com/Volmont85/ig-autopost. Токены и ID лежат
только в GitHub Secrets, в коде и в `queue.json` их быть не должно.

**Важно про среды исполнения.** У пользователя несколько Claude-поверхностей:
Claude Code на Маке (полный доступ — сеть и файлы) и Claude Desktop/Cowork в
изолированной песочнице. У песочницы **нет доступа в интернет**
(github.com блокируется firewall'ом песочницы, `git push`/`gh` не работают
и не будут — это не обходится) — но у неё **есть доступ к файлам этого
репозитория через инструмент `request_cowork_directory`** (файловый мост
Cowork-сессии, не сеть). Через него сессия в песочнице может читать/писать
файлы напрямую (Read/Write/Edit), в том числе `queue.json` и `media/`.

**Важно — НЕ трогай `.git` сама, даже если технически можешь.** Раньше
здесь советовалось делать `git add`/`git commit` локально через bash — это
формально работает, но на практике именно из-за этого несколько раз
намертво зависал `.git/index.lock` и `.git/HEAD.lock`: git-операции через
файловый мост Cowork идут медленнее и непредсказуемее обычного локального
git, и когда одновременно коммитить пытаются и ты, и локальный вотчер на
Маке — они конкурируют за один и тот же `.git`, и один из процессов
застревает или падает, оставляя lock-файл. Разгребать это дольше и больнее,
чем просто не создавать гонку. Поэтому: **только Read/Write/Edit файлов,
никакого `git add`/`git commit`/`git push`/`git fetch` через bash.** Всю
git-работу делает исключительно локальный автопуш на Маке (LaunchAgent,
следит за `media/` и `queue.json`, коммитит и пушит сам — см. раздел
«Автопуш и мгновенная публикация» ниже). `git push`/`git fetch`/`gh` тебе и
так недоступны (нет сети) — это не менялось.

Если ты сессия без сети (Cowork) и хочешь проверить, есть ли у тебя доступ
к файлам: проверь список доступных tools на `request_cowork_directory`
(или аналог), не полагайся на то, что писали в чате раньше — могло
измениться. Если моста нет вообще — единственный путь: готовить контент в
чате и отдавать его пользователю, чтобы он сам перенёс через Claude Code.

Тебе не нужно и невозможно проверить результат пуша изнутри песочницы (нет
сети) — просто сохрани файл и сообщи пользователю, что сделано, вотчер
разберётся сам в течение секунд.

## Черновики и предохранитель перед публикацией

**Если запись в `queue.json` добавляет не сам пользователь напрямую** (например,
контент подготовлен в другой Claude-сессии и просто переносится сюда) —
статус должен быть `"draft"`, а не `"pending"`. `run_queue.py` публикует
только `"pending"`, `"draft"` он полностью игнорирует. Это предохранитель:
контент может попасть в репозиторий и запуститься автопушем сам по себе, но
реально уйдёт в Instagram только после того, как кто-то осознанно сменит
`"draft"` → `"pending"` (пользователь просит это сделать явной фразой в
чате, либо делает сам через веб-редактор на github.com).

Локальный автопуш (LaunchAgent на Маке, см. ниже) коммитит и пушит **любые**
изменения в `media/` и `queue.json`, включая черновики — это нормально,
черновики просто лежат в репозитории неопубликованными, пока не одобрены.
Автопуш реагирует на изменения файлов **на диске Мака**, а не на что-либо,
происходящее в других Claude-сессиях напрямую — файлы туда должен положить
либо пользователь, либо Claude Code с реальным доступом к папке репозитория.

**Как только черновик подготовлен (файл лежит в `media/`, запись добавлена в
`queue.json` со `status: "draft"`) — сразу же явно спроси пользователя в
чате, публиковать ли его, не жди, пока он сам вспомнит проверить.** Например:
«Черновик "<id>" готов (фото/карусель/reel в <account>, подпись: "..."). Опубликовать
сейчас?». Если да — смени `"draft"` на `"pending"`, закоммить/запуши (или
дай это сделать автопушу, если файл уже в отслеживаемой папке) — дальше
публикация уйдёт в течение секунд благодаря push-триггеру. Если нет —
оставь как есть или спроси, что поправить.

## Как добавить публикацию (основной сценарий)

1. Положить медиафайл в `media/<account>/` (`personal` или `goszakupki`).
   - Фото/карусель: **только JPEG**, соотношение сторон 4:5–1.91:1.
   - Reels/видео в Stories: mp4, 9:16, 5–90 сек, H.264/HEVC + AAC.
   - Фото в Stories: JPEG, обычно 9:16.
2. Добавить запись в `queue.json` (это массив, дописать новый объект):

```json
{
  "id": "уникальный-id",
  "account": "personal",
  "type": "photo",
  "publish_at": "2026-08-01T09:00:00+03:00",
  "caption": "Текст с #хэштегами",
  "media": ["media/personal/foto.jpg"],
  "status": "pending"
}
```

   `type`: `photo` | `carousel` | `reel` | `story`.
   `media`: массив путей относительно корня репозитория (для carousel — 2–10 файлов).
   Для `reel` опционально: `"cover"` (путь к обложке), `"share_to_feed": false`
   (по умолчанию true), `"trial": true` + `"graduation_strategy": "MANUAL"` или
   `"SS_PERFORMANCE"` — публикация как **пробный рилс** (см. ниже).
   Для `story` подписи (`caption`) не поддерживаются самим Instagram — можно
   оставить `""`, она будет проигнорирована.

   `publish_at` — либо конкретное время (публикация по расписанию), либо
   **вообще не указывай поле** — тогда запись публикуется как можно скорее,
   как только дойдёт до GitHub (обычно 10–30 сек через push-триггер, плюс
   время на готовность файла в GitHub Pages для медиа). Это стандартный
   способ сказать «опубликуй сейчас» — отдельно указывать текущее время
   вручную не нужно, и уж тем более не нужно прибавлять к нему буфер
   «на всякий случай»: он ничего не чинит, публикация либо готова, либо нет.

   **Протокол для Claude Desktop/Cowork:** перед добавлением записи спроси
   пользователя «сейчас или по расписанию» — «сейчас» = не указывать
   `publish_at` вообще, «по расписанию» = явное время. Дальше как обычно —
   статус `"draft"`, спросить подтверждение, затем `"pending"`.

3. Закоммитить и запушить в `main`. Дальше система сама всё сделает: раз в
   30 минут (или по ручному запуску, см. ниже) GitHub Actions проверит, чья
   `publish_at` уже наступила (сравнение в UTC), проверит доступность файла
   по HTTPS, опубликует и допишет в ту же запись `status: "done"`,
   `published_at`, `media_id` (или `status: "failed"`, `error` при неудаче).

Это можно делать и без терминала — прямо в вебе на github.com: загрузить файл
через Add file → Upload files, отредактировать `queue.json` через встроенный
редактор, закоммитить.

## Опубликовать прямо сейчас, не дожидаясь расписания

```bash
gh workflow run publish.yml --repo Volmont85/ig-autopost
```

(Сеть до api.github.com у пользователя нестабильная — TLS-таймауты частые,
нормально повторить команду 3-5 раз подряд.) Проверить статус запуска:

```bash
gh run list --repo Volmont85/ig-autopost --workflow=publish.yml --limit 5
gh run view <run-id> --repo Volmont85/ig-autopost --log
```

## Пробные рилсы (Trial Reels)

Подтверждено реальной публикацией: параметр `trial_params` со значением
`{"graduation_strategy": "MANUAL"}` работает через API — реализовано в
`Account.publish_reel(..., trial=True, graduation_strategy="MANUAL")`.

Ограничение — не наше, а Instagram: функция должна быть доступна конкретному
аккаунту (на `goszakupki`, новом/пустом аккаунте, API вернул
`Application does not have permission for this action` — вероятно, из-за
малого числа подписчиков или того, что функция там ещё не разблокирована).
На `personal` сработало без проблем. Если тест на новом аккаунте не проходит —
это ожидаемо, не баг.

## Локальный тест (если нужно проверить руками)

```bash
cd ~/Projects/ig-autopost
source .venv/bin/activate
python ig_publish.py personal quota   # проверить квоту публикаций
```

Для реальной публикации из Python — `Account.from_env('personal')` и методы
`publish_photo` / `publish_carousel` / `publish_reel` / `publish_story`.
Токены читаются из переменных окружения `IG_<NAME>_ID` / `IG_<NAME>_TOKEN` —
их нет в этой сессии по умолчанию, пользователь должен экспортировать их сам
в терминале (см. ниже про секреты).

## Важно — секреты и подтверждения

- **Никогда не проси и не выводи в чат значения токенов/ID/App Secret.**
  Если нужно их куда-то передать — только через `gh secret set` (интерактивный
  ввод в терминале пользователя) или напрямую в GitHub Actions env.
- Любая публикация через `run_queue.py` / `workflow_dispatch` — это **реальный
  пост в Instagram**, необратимое действие (даже Stories видны 24 часа всем
  подписчикам). Всегда явно подтверждай с пользователем перед запуском, если
  не попросили действовать без подтверждений.
- `git push` в этот публичный репозиторий — тоже подтверждать, если не давали
  постоянного разрешения действовать автономно.

## Автопуш и мгновенная публикация

На Маке фоном работает LaunchAgent (`~/Library/LaunchAgents/
com.azimin.ig-autopost-autopush.plist`), который следит за `media/` и
`queue.json` в этой папке и сам делает `git add/commit/push` при любом
изменении (скрипт `~/ig-autopost-autopush.sh`, лог в `~/ig-autopost-autopush.log`).
`publish.yml` дополнительно триггерится на `push` в `main` (в пределах путей
`queue.json`, `media/**`) — значит запись со статусом `pending` публикуется
почти сразу после пуша, не дожидаясь ближайшего 30-минутного тика расписания.
Собственные коммиты самого workflow помечены `[skip ci]`, чтобы не зациклиться.

**Известный риск (уже случился один раз, уже исправлен, но держи в голове):**
несколько актёров (эта Claude Code сессия, Cloude через файловый мост,
локальный автопуш) могут почти одновременно писать/коммитить/пушить в один
и тот же `.git`. Из-за этого один раз реально задвоился пост в Instagram:
`publish.yml` успешно опубликовал (`media_id` получен), но при попытке
закоммитить `status: "done"` обратно в `queue.json` push был отклонён
(`! [rejected] ... fetch first`, кто-то ещё успел запушить первым) —
воркфлоу просто падал, факт публикации не сохранялся, следующий прогон
видел запись как всё ещё `"pending"` и публиковал заново. Почищено:
- В `publish.yml`, шаг «Commit updated queue.json»: при отклонённом push
  теперь `git fetch` + `git rebase origin/main` + повтор (до 6 раз), а не
  падение с концами.
- В `~/ig-autopost-autopush.sh`: любой `*.lock` под `.git` (не только
  `index.lock` — отдельно от него застревал и `HEAD.lock`, `git commit`
  создаёт оба независимо, и любой может зависнуть, если процесс прервался
  между ними), если он старше 90 секунд, считается брошенным и удаляется
  автоматически через `find .git -name "*.lock"`, а не по фиксированному
  списку имён. Первая версия фикса чистила только `index.lock` — этого не
  хватило, `HEAD.lock` всё равно вешал автопуш намертво, пришлось чинить
  во второй раз. Если увидишь третий подобный файл (например,
  `refs/heads/main.lock` при rebase) — `find` уже его подхватит сам, менять
  скрипт не нужно.

Тем не менее: если видишь, что публикация прошла, а `queue.json` при этом
почему-то всё ещё показывает `"pending"` для этой записи — **не запускай
публикацию повторно не разобравшись**, сначала проверь историю коммитов
(`git log`) и логи последнего прогона `publish.yml` на предмет отклонённого
push — велика вероятность, что публикация уже состоялась, просто статус не
записался.

## Прочее

- `refresh.yml` раз в неделю продлевает токены через `refresh_token.py`
  (`ig_refresh_token`, секрет не нужен) и обновляет GitHub Secrets через
  `gh secret set` (использует секрет `GH_PAT`).
- Квота публикаций проверяется перед стартом (`Account.quota()`), примерно
  100 публикаций в сутки на аккаунт.
- Зависимость только одна — `requests` (см. `requirements.txt`).
