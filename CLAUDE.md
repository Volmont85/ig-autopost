# ig-autopost

Автопостинг в три Instagram-аккаунта (`personal`, `goszakupki`, `realbuiltbyone`) через официальный
Instagram Graph API. Публикация идёт через GitHub Actions — раз в 2 минуты её
запускает heartbeat на Railway (`webhook/app.py`, до 24.08.2026 это делал
локальный процесс на Маке — см. «Автопуш и мгновенная публикация» ниже),
плюс push-триггер (мгновенно) и резервный `schedule` на GitHub.
Медиафайлы раздаются через GitHub Pages.

Репозиторий публичный: github.com/Volmont85/ig-autopost. Токены и ID лежат
только в GitHub Secrets, в коде и в файлах `queue/` их быть не должно.

## Формат очереди: один файл на запись (важно, изменилось)

Очередь — это папка `queue/`, где **каждая запись — отдельный файл
`queue/<id>.json`**, а не один общий массив `queue.json`. Так было не
всегда: раньше был единый `queue.json`, и это регулярно приводило к
git-конфликтам — GitHub Actions обновляет статус одной записи (`status:
"done"`, `media_id`) напрямую на GitHub, минуя Мак, а в это же время
локальный автопуш добавляет или меняет другую запись. Оба трогали один и
тот же файл, и построчный git-merge не справлялся, потому что в JSON-массиве
почти любая правка задевает соседние строки (запятую/скобку предыдущего
элемента). За один день так зависало **три раза подряд**, каждый раз
приходилось разруливать конфликт руками. Разбивка на отдельные файлы решает
это структурно: разные записи — разные файлы, конфликтовать почти нечему.

Формат содержимого файла — тот же набор полей, что раньше был у элемента
массива:

```json
{
  "id": "уникальный-id",
  "account": "personal",
  "type": "photo",
  "publish_at": "2026-08-01T09:00:00+03:00",
  "caption": "Текст с #хэштегами",
  "media": ["media/personal/foto.jpg"],
  "status": "pending"
}
```

`id` в содержимом файла должен совпадать с именем файла без `.json`
(`queue/<id>.json`). Не переиспользуй `id` для другого контента, даже если
кажется, что это «вторая версия» того же поста — раньше так уже путали
историю публикаций (`viskont-teaser-shot1-v2` дважды пытались занять разным
контентом). Для новой версии — новый `id` (например, добавь `-v2`, `-v3`
к базовому имени) и, соответственно, новый файл.

## Важно про среды исполнения

У пользователя несколько Claude-поверхностей: Claude Code на Маке (полный
доступ — сеть и файлы) и Claude Desktop/Cowork в изолированной песочнице.
У песочницы **нет доступа в интернет** (github.com блокируется firewall'ом
песочницы, `git push`/`gh` не работают и не будут — это не обходится) — но
у неё **есть доступ к файлам этого репозитория через инструмент
`request_cowork_directory`** (файловый мост Cowork-сессии, не сеть). Через
него сессия в песочнице может читать/писать файлы напрямую (Read/Write/
Edit), в том числе `queue/*.json` и `media/`.

**Важно — НЕ трогай `.git` сама, даже если технически можешь.** Раньше
здесь советовалось делать `git add`/`git commit` локально через bash — это
формально работает, но на практике именно из-за этого несколько раз
намертво зависал `.git/index.lock` и `.git/HEAD.lock`: git-операции через
файловый мост Cowork идут медленнее и непредсказуемее обычного локального
git, и когда одновременно коммитить пытаются и ты, и локальный вотчер на
Маке — они конкурируют за один и тот же `.git`, и один из процессов
застревает или падает, оставляя lock-файл. Поэтому: **только Read/Write/
Edit файлов, никакого `git add`/`git commit`/`git push`/`git fetch` через
bash.** Всю git-работу делает исключительно локальный автопуш на Маке (см.
раздел «Автопуш и мгновенная публикация» ниже). `git push`/`git fetch`/`gh`
тебе и так недоступны (нет сети) — это не менялось.

Если ты сессия без сети (Cowork) и хочешь проверить, есть ли у тебя доступ
к файлам: проверь список доступных tools на `request_cowork_directory`
(или аналог), не полагайся на то, что писали в чате раньше — могло
измениться. Если моста нет вообще — единственный путь: готовить контент в
чате и отдавать его пользователю, чтобы он сам перенёс через Claude Code.

Тебе не нужно и невозможно проверить результат пуша изнутри песочницы (нет
сети) — просто сохрани файл и сообщи пользователю, что сделано, вотчер
разберётся сам в течение секунд.

## Черновики и предохранитель перед публикацией

**Если запись добавляет не сам пользователь напрямую** (например, контент
подготовлен в другой Claude-сессии и просто переносится сюда) — статус
должен быть `"draft"`, а не `"pending"`. `run_queue.py` публикует только
`"pending"`, `"draft"` он полностью игнорирует. Это предохранитель: контент
может попасть в репозиторий и запуститься автопушем сам по себе, но реально
уйдёт в Instagram только после того, как кто-то осознанно сменит `"draft"`
→ `"pending"` (пользователь просит это сделать явной фразой в чате, либо
делает сам через веб-редактор на github.com).

Локальный автопуш (LaunchAgent на Маке, см. ниже) коммитит и пушит **любые**
изменения в `media/` и `queue/`, включая черновики — это нормально,
черновики просто лежат в репозитории неопубликованными, пока не одобрены.
Автопуш реагирует на изменения файлов **на диске Мака**, а не на что-либо,
происходящее в других Claude-сессиях напрямую — файлы туда должен положить
либо пользователь, либо Claude Code с реальным доступом к папке репозитория.

**Как только черновик подготовлен (файл лежит в `media/`, запись создана в
`queue/<id>.json` со `status: "draft"`) — сразу же явно спроси пользователя
в чате, публиковать ли его, не жди, пока он сам вспомнит проверить.**
Например: «Черновик "<id>" готов (фото/карусель/reel в <account>, подпись:
"..."). Опубликовать сейчас?». Если да — смени `"draft"` на `"pending"` в
том же файле, сохрани (или дай это сделать автопушу, если файл уже в
отслеживаемой папке) — дальше публикация уйдёт в течение секунд благодаря
push-триггеру. Если нет — оставь как есть или спроси, что поправить.

## Как добавить публикацию (основной сценарий)

1. Положить медиафайл в `media/<account>/` (`personal`, `goszakupki` или `realbuiltbyone`).
   - Фото/карусель: **только JPEG**, соотношение сторон 4:5–1.91:1.
   - Reels/видео в Stories: mp4, 9:16, 5–90 сек, H.264/HEVC + AAC.
   - Фото в Stories: JPEG, обычно 9:16.
2. Создать новый файл `queue/<уникальный-id>.json`:

```json
{
  "id": "уникальный-id",
  "account": "personal",
  "type": "photo",
  "publish_at": "2026-08-01T09:00:00+03:00",
  "caption": "Текст с #хэштегами",
  "media": ["media/personal/foto.jpg"],
  "status": "pending"
}
```

   `type`: `photo` | `carousel` | `reel` | `story`.
   `media`: массив путей относительно корня репозитория (для carousel — 2–10 файлов).
   Для `reel` опционально: `"cover"` (путь к обложке), `"share_to_feed": false`
   (по умолчанию true), `"trial": true` + `"graduation_strategy": "MANUAL"` или
   `"SS_PERFORMANCE"` — публикация как **пробный рилс** (см. ниже).
   Для `story` подписи (`caption`) не поддерживаются самим Instagram — можно
   оставить `""`, она будет проигнорирована.

   `publish_at` — либо конкретное время (публикация по расписанию), либо
   **вообще не указывай поле** — тогда запись публикуется как можно скорее,
   как только дойдёт до GitHub (обычно 10–30 сек через push-триггер, плюс
   время на готовность файла в GitHub Pages для медиа). Это стандартный
   способ сказать «опубликуй сейчас» — отдельно указывать текущее время
   вручную не нужно, и уж тем более не нужно прибавлять к нему буфер
   «на всякий случай»: он ничего не чинит, публикация либо готова, либо нет.

   **Протокол для Claude Desktop/Cowork:** перед добавлением записи спроси
   пользователя «сейчас или по расписанию» — «сейчас» = не указывать
   `publish_at` вообще, «по расписанию» = явное время. Дальше как обычно —
   статус `"draft"`, спросить подтверждение, затем `"pending"`.

3. Закоммитить и запушить в `main`. Дальше система сама всё сделает: раз в
   30 минут (или по ручному запуску, см. ниже) GitHub Actions проверит все
   файлы в `queue/`, чья `publish_at` уже наступила (сравнение в UTC),
   проверит доступность файла по HTTPS, опубликует и допишет в тот же файл
   `status: "done"`, `published_at`, `media_id` (или `status: "failed"`,
   `error` при неудаче).

Это можно делать и без терминала — прямо в вебе на github.com: загрузить
файл через Add file → Upload files (и в `media/`, и новый файл в `queue/`),
закоммитить.

## Опубликовать прямо сейчас, не дожидаясь расписания

```bash
gh workflow run publish.yml --repo Volmont85/ig-autopost
```

(Сеть до api.github.com у пользователя нестабильная — TLS-таймауты частые,
нормально повторить команду 3-5 раз подряд.) Проверить статус запуска:

```bash
gh run list --repo Volmont85/ig-autopost --workflow=publish.yml --limit 5
gh run view <run-id> --repo Volmont85/ig-autopost --log
```

## Пробные рилсы (Trial Reels)

Подтверждено реальной публикацией: параметр `trial_params` со значением
`{"graduation_strategy": "MANUAL"}` работает через API — реализовано в
`Account.publish_reel(..., trial=True, graduation_strategy="MANUAL")`.

Ограничение — не наше, а Instagram: функция должна быть доступна конкретному
аккаунту (на `goszakupki`, новом/пустом аккаунте, API вернул
`Application does not have permission for this action` — вероятно, из-за
малого числа подписчиков или того, что функция там ещё не разблокирована).
На `personal` сработало без проблем. Если тест на новом аккаунте не проходит —
это ожидаемо, не баг.

## Важно — секреты и подтверждения

- **Никогда не проси и не выводи в чат значения токенов/ID/App Secret.**
  Если нужно их куда-то передать — только через `gh secret set` (интерактивный
  ввод в терминале пользователя) или напрямую в GitHub Actions env.
- Любая публикация через `run_queue.py` / `workflow_dispatch` — это **реальный
  пост в Instagram**, необратимое действие (даже Stories видны 24 часа всем
  подписчикам). Всегда явно подтверждай с пользователем перед запуском, если
  не попросили действовать без подтверждений.
- `git push` в этот публичный репозиторий — тоже подтверждать, если не давали
  постоянного разрешения действовать автономно.

## Автопуш и мгновенная публикация

На Маке фоном работает LaunchAgent (`~/Library/LaunchAgents/
com.azimin.ig-autopost-autopush.plist`), который следит за `media/`,
`queue/` и `CLAUDE.md` в этой папке и сам делает `git add/commit/push` при
любом изменении (скрипт `~/ig-autopost-autopush.sh`, лог в
`~/ig-autopost-autopush.log`). `publish.yml` дополнительно триггерится на
`push` в `main` (в пределах путей `queue/**`, `media/**`) — значит запись
со статусом `pending` публикуется почти сразу после пуша, не дожидаясь
ближайшего тика расписания. Собственные коммиты самого
workflow помечены `[skip ci]`, чтобы не зациклиться.

**История инцидентов с этим механизмом (все исправлены, но держи в голове —
это живой, регулярно проверяемый на практике участок системы):**

1. **Задвоенная публикация.** Несколько актёров почти одновременно писали/
   коммитили/пушили в один `.git`. `publish.yml` успешно публиковал
   (`media_id` получен), но при попытке закоммитить `status: "done"` push
   отклонялся (`! [rejected] ... fetch first`) — воркфлоу падал, факт
   публикации не сохранялся, следующий прогон видел запись как всё ещё
   `"pending"` и публиковал заново. Фикс — в `publish.yml`, шаг «Commit
   updated queue entries»: при отклонённом push `git fetch` + `git rebase
   origin/main` + повтор (до 6 раз), а не падение с концами.

2. **Зависший `.git/index.lock` / `.git/HEAD.lock`.** Git-commit создаёт
   оба лока независимо, любой может зависнуть, если процесс прервался между
   ними. В `~/ig-autopost-autopush.sh`: любой `*.lock` под `.git` старше 90
   секунд считается брошенным и удаляется через `find .git -name "*.lock"`
   (не фиксированный список файлов — подхватит и будущие подобные).

3. **~13-часовой простой пуша.** У локального автопуша был свой `git push`
   без `fetch`/`rebase` — тот же класс бага, что в п.1, но забыли применить
   на локальной стороне. `publish.yml` коммитит `status: "done"` напрямую на
   GitHub, минуя Мак — локальный `main` отстаёт, и обычный push без
   fetch/rebase проваливается ВСЕГДА одинаково, retry не помогает. Фикс —
   тот же паттерн `git fetch` + `git rebase origin/main` теперь и в
   `~/ig-autopost-autopush.sh`.

4. **Разбивка `queue.json` → `queue/<id>.json` (структурный фикс, а не
   патч).** Пункты 1-3 лечили симптомы retry-логикой, но настоящие
   конфликты содержимого (когда два актёра меняют один и тот же файл в
   одно и то же время) retry не решает — нужно ручное разрешение
   (`rebase failed, needs manual resolution` в логе). За один день это
   случилось трижды подряд с единым `queue.json`. Переход на отдельный файл
   на запись убирает саму возможность такого конфликта в подавляющем
   большинстве случаев: GitHub Actions обновляет статус в файле записи А,
   вотчер добавляет новый файл записи Б — они физически не пересекаются.

Если увидишь в `~/ig-autopost-autopush.log` строку `rebase failed, needs
manual resolution` — это настоящий конфликт содержимого (два актёра
одновременно меняли один и тот же файл `queue/<id>.json`), retry не
поможет, разбираться руками: `cd ~/Projects/ig-autopost && git status`,
сравнить `git show origin/main:queue/<id>.json` с локальной версией, взять
авторитетное состояние с GitHub (если запись там уже `"done"` — значит,
публикация реально состоялась) и свести вручную.

5. **`schedule`-триггер GitHub Actions систематически дропает тики, а не
   просто немного опаздывает.** Замерено эмпирически на реальных данных
   (31 июля — 2 августа): при cron `*/30 * * * *` фактический средний
   интервал между срабатываниями `schedule` составил **~102 минуты вместо
   30** — то есть ~70% тиков GitHub просто не выполнил, не только опоздал.
   Из-за этого запланированные посты (Stories/Reels с конкретным
   `publish_at`, без нового push рядом с этим временем) уходили с задержкой
   30–90+ минут. Причина — вероятно, fair-use throttling на стороне GitHub
   из-за общего объёма запусков этого репозитория (~25/сутки push+schedule
   вместе), это не гарантированно, но `workflow_dispatch` (прямой API-вызов)
   такому дропу не подвержен. Фикс — не полагаться на `schedule` для
   точности вообще: второй LaunchAgent на Маке
   (`~/Library/LaunchAgents/com.azimin.ig-autopost-heartbeat.plist`,
   скрипт `~/ig-autopost-heartbeat.sh`, лог `~/ig-autopost-heartbeat.log`)
   каждые 5 минут (`StartInterval: 300`, не `WatchPaths` — это по таймеру,
   не по изменению файлов) сам вызывает `gh workflow run publish.yml`.
   Максимальное опоздание запланированной публикации = интервал heartbeat
   (5 минут); на мгновенную публикацию (без `publish_at`) heartbeat не
   влияет — та уходит через push-триггер за секунды, независимо от него.
   **Важно:** смещать `StartInterval` на «нечётную» минуту НЕ нужно и не
   имеет смысла — это прямой вызов `workflow_dispatch` конкретно с этой
   машины, а не `schedule`-событие, которое стоит в общей очереди с cron
   других репозиториев; к тому же `StartInterval` в launchd и так не
   привязан к границам часа, а считает от момента загрузки агента. Само
   собой `gh` в скрипте — абсолютный путь `/opt/homebrew/bin/gh`, не
   просто `gh` — launchd запускает процессы с урезанным `PATH`, где
   Homebrew-бинарники не резолвятся, и это уже один раз стреляло
   (`gh: command not found` в логе при первом запуске).

   **Обновление 24.08.2026 — heartbeat переехал с Мака на Railway.** Логика
   выше (зачем вообще нужен heartbeat, почему не полагаться на `schedule`)
   не изменилась, изменилось только ГДЕ он живёт: теперь это фоновый поток
   в `webhook/app.py` (тот же процесс, что уже держит вебхук для лид-магнита
   — см. раздел про Railway ниже), тикает каждые 2 минуты (было 5),
   независимо от того, включён ли Мак. `~/ig-autopost-heartbeat.sh` на
   Маке остался, но только ради синка git на локальную копию для Desktop/
   Cowork — `gh workflow run` он больше не вызывает.

   `schedule` в `publish.yml` остаётся резервным триггером (на случай, если
   Мак выключен/спит) — там смещение минуты действительно помогает: cron
   стоит на `3,33 * * * *`, а не `*/30 * * * *`, чтобы не целиться в те же
   ровные `:00`/`:30`, куда бьёт cron большинства чужих репозиториев на
   GitHub — именно там инфраструктура перегружена сильнее всего.

6. **`.DS_Store` от Finder заблокировал rebase у автопуша (06.08.2026).**
   `media/.DS_Store` в какой-то момент случайно попал под git-контроль (его
   подмёл `git add media queue CLAUDE.md` в автопуше — команда добавляет
   всё под этими путями без разбора). Finder периодически переписывает
   `.DS_Store` просто при открытии папки в нём — с точки зрения git это
   реальное изменение отслеживаемого файла. Когда автопуш пытался
   перебазироваться на свежий коммит с GitHub, `git rebase` падал с `cannot
   rebase: You have unstaged changes` (лог: `~/ig-autopost-autopush.log`),
   локальная ветка расходилась с `origin/main` и зависала с непрошедшим
   пушем — снаружи это выглядело как «статистика/очередь не обновляются»,
   хотя GitHub Actions всё собирал исправно, просто изменения не доходили
   до Мака. Фикс структурный: `.DS_Store` добавлен в `.gitignore`,
   `media/.DS_Store` снят с отслеживания (`git rm --cached`) — Finder может
   переписывать его сколько угодно, `git status` это больше не увидит.

**Тем не менее:** если видишь, что публикация прошла, а файл записи при
этом почему-то всё ещё показывает `"pending"` — **не запускай публикацию
повторно не разобравшись**, сначала проверь историю коммитов (`git log`) и
логи последнего прогона `publish.yml` на предмет отклонённого push — велика
вероятность, что публикация уже состоялась, просто статус не записался.

## Статистика и разбор эффективности

`stats.py` + `stats.yml` собирают метрики опубликованных постов через Graph API
и складывают их **в репозиторий файлами** — это принципиально: сессии без сети
(Claude Desktop/Cowork) не могут прочитать лог GitHub Actions, но читают файлы
через файловый мост. Раньше `stats.yml` только печатал отчёт в лог, поэтому
цифры были доступны лишь в браузере.

```
stats/history.jsonl   append-only, одна строка = один замер одного поста
stats/latest.json     последний замер по каждому посту (быстрое чтение)
stats/followers.jsonl append-only, одна строка = один замер подписчиков аккаунта
stats/report.md       готовый разбор: подписчики + срезы по часу, дню недели, теме, типу
```

**Подписчики — отдельная гранулярность от постов.** `history.jsonl` про посты
(разный возраст жизни, расписание замеров, чтобы не жечь лимиты), а
`followers.jsonl` — про аккаунт целиком, замеряется при каждом прогоне
(`Account.account_fields()`, поле `followers_count`, разрешений сверх
`instagram_business_basic` не требует). Дешёвый вызов, расписание как у постов
не нужно. Замеряется для каждого аккаунта, у которого есть хоть одна запись в
`queue/` — новый аккаунт без единой публикации тоже попадёт в отчёт, как
только появится первая запись (даже `draft`). В отчёте — текущее число и
дельта за 24ч/7дней на аккаунт.

**Почему временной ряд, а не одна цифра.** Рилс копит просмотры неделями, так
что «сколько у него просмотров» зависит в основном от того, когда посмотрели.
Поэтому при каждом прогоне дописывается новый замер с `age_hours`, а в отчёте
посты сравниваются в ОДИНАКОВОМ возрасте (по умолчанию ~24 часа, допуск ±12).
Только такое сравнение честное.

Расписание замеров внутри `stats.py` (экономит вызовы API): моложе суток —
каждый прогон, до недели — раз в 20 часов, до 30 дней — раз в 6 дней, дальше
не трогаем. **Stories замеряются только первые 24 часа**: после этого
Instagram insights по ним не отдаёт вообще, данные теряются навсегда. Поэтому
cron стоит каждые 6 часов, а не раз в сутки: это запас на дроп schedule-тиков
(см. инцидент 5 выше), чтобы каждая сторис попала хотя бы в один прогон.

Ручной запуск: `gh workflow run stats.yml --repo Volmont85/ig-autopost`
(с `-f force=true` — перезамерить всё, игнорируя расписание).
Пересобрать только отчёт из уже собранной истории, без запросов к API:
`python stats.py --report`.

Необязательные поля в `queue/<id>.json`, которые улучшают отчёт: `"topic"`
(тема одним словом, иначе берётся первый хэштег) и `"hook"` (первая фраза
ролика, иначе берётся первая строка `caption`). Заполнять их стоит: без
`topic` срез «какие темы заходят» строится по хэштегам и получается грубее.

## Автоответы на комментарии и личные сообщения

Добавлено 06.08.2026, пока только для `realbuiltbyone` (первый аккаунт, на
котором включили). Отдельная подсистема от публикации — `ig_reply.py` +
workflow `reply.yml`, вызывается heartbeat'ом на Railway раз в 2 минуты наравне
с `publish.yml` (не блокируют друг друга при сбое одного из них).

**Как работает.** Опрос по расписанию (не webhooks — в проекте принципиально
нет постоянно работающего сервера, поэтому real-time push от Meta принимать
негде; альтернатива обсуждалась и отклонена сознательно). Для комментариев
берутся посты этого аккаунта из `queue/*.json` со `status: "done"`,
опубликованные не позже 14 дней назад (старые почти не получают новых
комментариев, не тратим вызовы API). Для сообщений — все диалоги через
`GET /{ig-id}/conversations`.

Каждый новый комментарий/сообщение уходит в Claude (`claude-sonnet-5` по
умолчанию, переопределяется переменной `REPLY_MODEL`) с инструментом
`decide_reply`, который обязан вернуть либо `action: "reply"` с текстом
ответа, либо `action: "skip"` с причиной. Отправляется только `reply` —
это не approval-gate для обычного контента (решение пользователя —
отвечать сразу, без подтверждения человеком), а узкий предохранитель
именно для того, что Claude сам сочтёт спамом, угрозой, самоповреждением
или вне своей компетенции (цены, юридические обязательства, персональные
данные) — такое остаётся неотвеченным до ручного разбора.

**Состояние** — `replies/<account>/answered_comments.json` и
`answered_messages.json`, коммитятся в репозиторий тем же workflow'ом
(паттерн identичен `stats/`). Без этого при каждом опросе слались бы
повторные ответы на одно и то же. Комментарий, у которого уже есть хоть
один ответ в ветке (свой или из старой ручной переписки), помечается
обработанным без обращения к Claude — не перебиваем существующий ответ.

**Новые разрешения и секреты.** Нужны `instagram_business_manage_comments`
и `instagram_business_manage_messages` в Meta App Dashboard (их не было в
исходной настройке — только `instagram_business_basic` и
`instagram_business_content_publish`) и перевыпущенный с этими разрешениями
токен. Плюс новый секрет `ANTHROPIC_API_KEY` — раньше в проекте не было
обращений к Claude API во время выполнения, только сам Claude Code/Desktop
интерактивно готовили контент.

**Не проверено ещё.** В отличие от публикации, эта подсистема пока не
протестирована реальным комментарием/сообщением (это разовое, не
управляемое расписанием событие — сложно устроить контролируемый тест).
Если увидишь странности (двойные ответы, не тот тон, пропущенные
сообщения) — не списывай на баг сразу, это первый прогон в проде.

## Лид-магнит по кодовому слову (goszakupki)

Добавлено 24.08.2026, только для `goszakupki` (IG `goszakupki.info` +
Telegram-канал `@goszakupki_help`). Отдельная от `ig_reply.py` подсистема —
`ig_leadmagnet.py`, детальный сценарий диалога и обоснование каждого шага
см. `lead-magnet-igtg-setup-claude-code.md`. Коротко: комментарий с кодовым
словом под постом → Private Reply (текст) + публичный ответ под
комментарием (случайный из 18 вариантов, не повторяет последние 3) → как
только человек хоть что-то ответил → кнопка «Да, пришли» → две «проверки»
подписки по `followers_count` (не блокирующие технически — честно
залогированный вовлекающий элемент, не настоящий гейт) → ссылка на
Telegram-бота `@goszakupkiinfo_bot`, где уже идёт настоящая проверка
подписки через `getChatMember` (Часть Б, отдельный бот через BotFather —
`tg_leadmagnet_bot.py`, добавлено 24.08.2026, см. отдельный раздел ниже).

**Почему нужен вебхук, а не только опрос.** Meta отдаёт нажатие Quick Reply
кнопки (`message.quick_reply.payload`) ТОЛЬКО через вебхук — этого поля
физически нет в ответе обычного `GET .../messages`, которым живёт весь
остальной проект (сверено по официальному Message Reference API, 24.08.2026,
несколько раз, включая живой прогон). Поэтому кроме поллинга есть тонкий
вебхук-приёмник на Railway (`webhook/`, см. `webhook/README.md`) — он
только проверяет подпись Meta и пересылает нажатие в GitHub через
`repository_dispatch`, вся логика остаётся в Actions, никакого состояния
на Railway нет. Публичный URL:
`https://webhook-production-3b88.up.railway.app/webhook`.

**Два независимых workflow, один и тот же `state.json` — общая
concurrency-группа `leadmagnet-ig`:**

- `leadmagnet_ig.yml` — поллинг (heartbeat раз в 5 минут + резервный
  `schedule`): новые комментарии с кодовым словом (Private Reply + публичный
  ответ), новые ответы в уже открытых диалогах (→ кнопка «Да, пришли»).
- `leadmagnet_ig_webhook.yml` — `repository_dispatch: types: [ig_quick_reply]`,
  реакция на конкретное нажатие кнопки (LM_YES → LM_CHECK_1 → LM_CHECK_2).

Обе трогают `leadmagnet/goszakupki/state.json` — без общей concurrency-группы
это была бы ровно та же гонка, что уже один раз задвоила публикацию рилса
(`run_queue.py`, инцидент 2026-08-19) — дешевле не подпускать воркфлоу друг
к другу вообще, чем городить ту же claim-логику ради двух workflow.

**Состояние и данные:**

```
leadmagnet/<account>/state.json                  по IG user_id: code, stage, t0/t1/t2
leadmagnet/<account>/recent_reply_variants.json   последние 3 индекса публичного ответа
leadmagnets/<account>.json                        тексты лид-магнитов по кодовым словам
stats/leadmagnet-conversion.jsonl                 append-only, t0/t1/t2 + дельты на завершённую воронку
```

Ключ состояния — реальный IG `user_id`, а не `comment_id`: ответ API на
Private Reply содержит `recipient_id` (подтверждено официальной
документацией Private Replies) — это и есть Instagram-scoped ID
комментатора, используется сразу, без сопоставления диалогов эвристикой.

**Защита от повторных/чужих нажатий кнопки** — `handle_quick_reply` сверяет
`stage` записи с тем, какая кнопка ожидается: нажатие не той стадии (повтор
после `done`, или payload без существующей записи) молча игнорируется, не
трогает уже посчитанные `t0/t1/t2`.

**`leadmagnets/goszakupki.json` — заполняется постепенно.** Восемь кодовых
слов (`ВЫПИСКА`, `ПРОВАЛ`, `ЗАКАЗЧИК`, `СКИДКА`, `ПОРЯДОК`, `ШТРАФ`, `ОТКАЗ`,
`ТЕНДЕР`) на месте; Claude Desktop пишет туда реальные `title`/`text`
напрямую через файловый мост (обычный Read/Write/Edit, без `git` — автопуш
на Маке сам заберёт, `leadmagnets` уже в его `WatchPaths`). На 24.08.2026
заполнены VYPISKA/PROVAL/OTKAZ, остальные ещё `TODO: ...`. `title` уходит в
реальные сообщения Instagram сразу; `text` — то, что реально выдаёт
`tg_leadmagnet_bot.py` после подтверждённой подписки (см. ниже) — раньше
никуда не читалось, теперь читается.

## Telegram-бот лид-магнита (Часть Б, @goszakupkiinfo_bot)

`tg_leadmagnet_bot.py` + `leadmagnet_tg.yml` (heartbeat + резервный `schedule`,
своя concurrency-группа `leadmagnet-tg` — не пересекается с `leadmagnet-ig`,
разные файлы состояния). **Не путать** с `telegram_work`/`telegram_personal`
(MCP для личного/рабочего аккаунта Александра, MTProto/Telethon) — это
отдельный полноценный бот через обычный Bot API, заведён в `@BotFather`.

Поток: `/start <CODE>` (переход по ссылке из Instagram) → предложение
подписаться на `@goszakupki_help` + инлайн-кнопка «Проверить подписку»
(`callback_data: "CHECK:<CODE>"`) → по нажатию `getChatMember(channel,
user_id)` → `member`/`creator`/`administrator` — выдать `text` из
`leadmagnets/goszakupki.json` по `CODE`; `left`/`kicked`/`restricted` —
честно «пока не вижу подписки», та же кнопка, нажимать можно сколько
угодно раз.

**Без вебхука, в отличие от Instagram-стороны.** Telegram Bot API отдаёт
нажатия инлайн-кнопок (`callback_query`) прямо в ответе `getUpdates` —
поллинга достаточно, Railway тут не участвует вообще.

Состояние — `leadmagnet_tg/state.json`, только `offset` для `getUpdates`
(коммитится тем же паттерном, что остальные состояния в проекте — иначе
каждый прогон переобрабатывал бы все апдейты заново).

**Секреты**: `TG_LEADMAGNET_BOT_TOKEN` (из `@BotFather`), нужен бот
администратором в `@goszakupki_help` (иначе `getChatMember` не сработает),
`TG_GOSZAKUPKI_HELP_CHAT_ID` (chat_id канала, через `getChat` после того как
бот стал админом). Плюс repo variable `TG_LEADMAGNET_BOT_USERNAME` (без
`@`, уже проставлена: `goszakupkiinfo_bot`) — читает `ig_leadmagnet.py` для
генерации ссылки `t.me/<username>?start=<CODE>` на шаге LM_CHECK_2.

**Публичные ответы под комментарием** — 18 вариантов в
`PUBLIC_REPLY_VARIANTS` внутри `ig_leadmagnet.py` (не в `leadmagnets/*.json`
— это не контент лид-магнита, а generic-подтверждения, общие для всех
кодовых слов). Большинство явно напоминают проверить «запросы» — Instagram
часто кидает сообщения от людей, с которыми раньше не переписывались, в
отдельную папку «Запросы на сообщения», которую многие не проверяют по
умолчанию; явное напоминание реально поднимает шанс, что получатель найдёт
сообщение (паттерн подсмотрен у `dmitriymarketing`, 24.08.2026).

**Сознательно НЕ стали делать искусственную задержку** перед публичным
ответом (обсуждали: очередь на heartbeat дала бы нечестные «плюс-минус
5 минут» вместо заявленных «пары минут», а таймер на Railway вернул бы туда
состояние, которое мы специально оттуда убрали). Разнообразие текста уже
решает задачу «не похоже на бота» — задержка добавила бы только сложность
без замечаемого эффекта.

## Прочее

- `refresh.yml` раз в неделю продлевает токены через `refresh_token.py`
  (`ig_refresh_token`, секрет не нужен) и обновляет GitHub Secrets через
  `gh secret set` (использует секрет `GH_PAT`).
- Квота публикаций проверяется перед стартом (`Account.quota()`), примерно
  100 публикаций в сутки на аккаунт.
- Зависимость только одна — `requests` (см. `requirements.txt`).
